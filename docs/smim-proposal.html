01 — 프로젝트 범위

이 프로젝트는 스토어 출시에서 끝난다

완료 지점을 먼저 확정한다. 범위가 정해져야 일정과 법적 요건이 따라 결정되기 때문이다.

완료 정의 앱이 스토어에 출시되고 성능 측정과 발표를 마치는 시점
포함
서버·앱 개발, 배포, 스토어 등록 및 출시, 성능 실험, 발표 자료
제외
출시 이후의 지속 운영, 사용자 확보, 수익화

발표 이후 서비스를 계속 공개 운영할지는 프로젝트 종료 후 별도로 판단한다. 포트폴리오로서의 목표는 "출시했고 이런 결과를 얻었다"까지이며, 영구 운영이 전제되지 않는다.

법적 요건이 여기서 갈린다

위치기반서비스사업 신고는 계속 운영을 선택할 경우에만 필요하다. 소상공인·1인 창조기업은 사업 개시 후 1개월의 유예가 있으며, 본 프로젝트의 출시는 마지막 1~2주에 일어나므로 프로젝트 기간 내에는 해당되지 않는다. 계속 운영을 택하면 그때 사업자등록과 신고를 진행한다.

02 — 문제 정의

공간에 쌓인 이야기를 읽을 방법이 없다

실제 공간에는 그 자리에 있어야만 의미가 생기는 정보가 존재한다. 이 골목의 분위기, 작년 봄 이 자리에 벚꽃이 어땠는지, 여기서 누가 무엇을 기다렸는지 같은 것들이다.

그런데 기존 서비스는 이 정보를 담지 못한다. 메신저는 사람 → 채팅방 → 대화의 구조라 아는 사람과의 대화만 담긴다. SNS는 위치를 태그로만 쓰기 때문에 게시물이 장소가 아니라 계정에 귀속된다. 지도 리뷰는 상점 정보에 한정된다.

결과적으로 장소에 귀속되어 시간이 지나도 그 자리에 남는 기록을 담을 그릇이 비어 있다. 물리적으로는 방명록, 낙서, 손편지가 하던 역할이다.

내가 지금 서 있는 이 자리에, 이전에 온 사람들은 무슨 이야기를 남겼을까?
03 — 핵심 컨셉

방에 들어가는 것이 아니라, 자리에 서면 읽힌다

스밈에는 채팅방이라는 개체가 존재하지 않는다. 메시지가 좌표를 가지고, 사용자의 화면은 자기 위치를 중심으로 한 공간 질의의 결과다. 입장도 퇴장도 없고, 고를 목록도 없다. 앱을 열면 이미 그 자리의 이야기가 흐르고 있다.

같은 메시지가 누가 언제 오느냐에 따라 성격이 달라진다. 지금 근처에 있는 사람에게는 실시간 대화로 도착하고, 세 달 뒤 그 자리에 오는 사람에게는 기록으로 읽힌다. 이 두 가지를 동시에 만족시키는 것이 이 서비스의 설계 목표다.

시간 구분선이 곧 콘텐츠다 일반 메신저에서 날짜 구분선은 단순 정보지만, 여기서는 “8개월 후”라는 줄 자체가 이 서비스에서만 볼 수 있는 장면이다. 공간은 고정된 채 시간만 건너뛰는 것이 눈에 보인다. UI 작업의 최우선 대상.
이름이 아니라 표식이다 닉네임을 붙이는 순간 정체성이 생기고, 정체성은 관계를 만들며, 결국 벗어나려던 사람 중심 구조로 되돌아간다. 대신 도형과 색으로 된 표식만 붙인다. 표식은 구분선으로 나뉜 구간 안에서만 유효하므로, 위아래의 같은 ●는 서로 다른 사람이다. 읽는 사람은 “저 사람”이 아니라 “저 줄”로 인식한다.
인용 답글이 이름을 대신한다 이름이 없을 때 유일한 결손은 “누구에게 하는 말인가”인데, 인용이 이를 완전히 해결한다. 1년 전 글에 답장이 도착하는 것이 이 앱의 가장 좋은 장면이 된다.
내 글만 구분된다 남은 구분되지 않고 나만 구분된다. 자기 글을 삭제하고 반응을 확인하기 위한 최소한의 장치.
04 — 핵심 설계 결정

여섯 개의 결정이 나머지를 정한다

기획 단계에서 확정한 사항. 이후 모든 구현은 여기에서 파생된다.

D1

반경의 중심은 사용자다 확정

지도를 격자로 미리 나누어 “같은 칸 = 같은 방”으로 묶지 않는다. 각 사용자는 자기 위치를 중심으로 한 반경을 보며, 따라서 A와 B가 보는 화면은 서로 다르다.

격자 방식은 경계선 문제를 만든다. 50m 떨어진 두 사람이 칸이 달라 서로 보지 못하는 상황이 발생하고, 번화가 한복판에 인위적인 선이 그어진다. 사용자 중심 반경에는 경계가 없다. 대신 “방”이라는 개체가 사라지므로 데이터 모델이 메시지 = 좌표를 가진 점으로 단순해진다.

D2

반경은 밀도에 따라 바뀌지 않는다 동적 폐기

지역의 메시지 밀도에 따라 반경을 조정하지 않는다. 메시지가 적은 지역에서는 반경이 아니라 시간 범위가 넓어진다. 기본값은 300m이며 확정값이 아니다 — 서버 설정으로 내려주고 A/B 실험(9주차)으로 최종 결정한다.

동적 반경을 버린 이유 — 메시지 수를 기준으로 반경을 조정하면 한적한 지역에서 반경이 수 km까지 늘어난다. 그 순간 “그 자리”라는 전제가 무너진다. 8km 떨어진 곳을 같은 공간이라 부를 수 없기 때문이다. 반면 반경을 좁히는 방향은 장소성을 해치지 않지만, 그 이득만으로는 동적 조정의 복잡도를 정당화하지 못한다.

고정해도 되는 이유 — 영구 저장(D3)을 택했으므로 같은 자리에 시간이 쌓인다. 한적한 지역에서는 첫 화면이 몇 년치로 채워질 뿐, 화면이 비지 않는다. 동적 반경은 TTL이 있던 설계의 잔재였다. 공간은 고정하고 시간을 푼다.

유지 반경을 두는 이유 — GPS 오차로 경계 근처 메시지가 나타났다 사라지며 화면이 깜빡인다. 한 번 로드된 메시지를 반경의 1.5배까지 붙잡아 두면 좌표가 흔들려도 읽던 글이 사라지지 않는다. 이 장치 덕분에 반경을 작게 잡을 수 있다.

부수 효과 — 모든 사용자가 같은 반경을 쓰므로 A가 B를 보면 B도 A를 본다. 비대칭 문제가 사라지고 조회와 실시간의 경로 분리도 불필요해진다. 밀도 집계와 반복 질의도 함께 삭제된다.

D3

메시지는 만료되지 않는다 TTL 폐기

일정 시간 후 자동 삭제하지 않는다. 메시지는 좌표에 영구히 남는다.

휘발형 설계에서는 주변에 아무도 없을 때 쓴 첫 메시지가 아무에게도 읽히지 않고 사라진다. 사용자 수가 적은 초기에 이는 치명적이다. 영구 저장은 콜드 스타트 문제를 동시 접속자 수가 아니라 시간으로 해결한다. 첫 사용자 한 명의 글도 한 달 뒤 그 자리를 지나는 사람에게 읽힌다. 다만 그 대가로 모더레이션 난이도가 크게 올라간다(→ 07).

D4

이름은 없고, 구간 표식만 있다 수정

닉네임도, “익명A” 같은 이름형 식별자도 쓰지 않는다. 대신 도형과 색으로 된 표식을 메시지에 부여하며, 이 표식은 시간 구분선으로 나뉜 구간 안에서만 유효하다. 같은 사람도 구간이 바뀌면 다른 표식을 받는다.

도형 6 × 색 4 = 24조합 · 도형이 1차 구분, 색은 보조

이름을 쓰지 않는 이유 — 이름은 아무리 무의미해도 정체성을 만들고, 정체성은 관계를 만들며, 결국 벗어나려던 사람 중심 구조로 되돌아간다. 도형은 그런 축적이 일어나지 않는다. 읽는 사람이 “저 사람”이 아니라 “저 줄”로 인식한다.

표식을 아예 없애지 않는 이유 — 여러 명이 동시에 말할 때 발화자 구분이 불가능해 대화가 해독되지 않는다. 그리고 이 문제는 시간이 지나도 사라지지 않는다. 지금 읽는 데 표식이 필요했다면 3개월 뒤 읽는 사람에게도 필요하므로, 표식은 메시지에 영구히 저장한다.

구간 단위인 이유 — 전역에서 유일할 필요가 없다. 한 화면 구간에 동시에 등장하는 발화자는 대개 3~6명이고, 시간 구분선이 이미 대화의 경계를 그리고 있다. 구간마다 표식을 재배정하면 전체 사용자 수와 무관해지며, 구분선 위아래의 같은 기호를 동일인으로 오해하지 않는다. 색각 이상을 고려해 도형부터 모두 소진한 뒤 색을 추가하는 순서로 배정하고, 한 구간에 24명을 넘기면 그 이후는 표식 없이 표시한다.

서버는 기기 단위 익명 키를 보관하며 이는 절대 노출되지 않는다. 자기 글 삭제, 도배 방지, 차단 처리는 내부 식별자 없이 구현할 수 없고, 차단은 스토어 심사 필수 요건이다. “표시하지 않되 보관한다”를 개인정보처리방침에 명시하고, 완전 익명이 아니라 가명(pseudonymous)으로 기술한다.

D5

실시간과 기록을 동시에 확정

메시지 작성 시 PostgreSQL 영구 저장과 WebSocket 실시간 전달을 함께 수행한다.

영구 저장만 하면 “REST 조회로 충분하지 않은가”라는 질문에 답할 수 없고, 이 프로젝트의 기술적 중심인 선택적 브로드캐스트가 근거를 잃는다. 둘을 함께 두면 지금 반경 안에 있는 사람에게는 대화가 되고, 나중에 오는 사람에게는 방명록이 된다.

D6

관계 대신 반응으로 재방문을 만든다 신규

팔로우·프로필·DM 같은 관계 기능을 넣지 않는다. 대신 내가 남긴 글에 달린 답글을 알린다. MVP에서는 앱을 열었을 때 보이는 인앱 표시까지만 구현하고, FCM 푸시는 확장으로 분리한다. 기기 익명 키에 연결되므로 익명은 유지된다.

대부분의 소셜 서비스는 관계를 재방문 동력으로 쓴다. 그러나 스밈은 위치 기반이라 같은 사람을 다시 만날 확률이 매우 낮고, 닉네임을 붙여도 반복 접촉이 없으면 관계는 생기지 않는다. 결국 익명의 자유는 잃고 관계는 얻지 못하는 최악의 절충이 된다. 진짜 관계를 만들려면 프로필·팔로우·DM까지 필요한데, 그것은 다른 서비스이며 오픈카톡·동네생활이 이미 점유하고 있다.

답글 알림은 관계가 아니라 내 흔적에 대한 피드백이다. 누가 답했는지 몰라도 되고, 중요한 것은 “내가 남긴 것이 읽혔다”는 사실이다. 3개월 전 내 글에 답장이 도착했다는 알림은 스밈에서만 가능한 경험이며, 익명을 유지하면서 재방문 동기를 만드는 사실상 유일한 장치다.

05 — 유사 서비스 분석

06 — 시스템 설계

Redis는 지금, PostGIS는 전부

영구 저장을 택하면서 두 저장소의 역할 분리가 명확해졌다. Redis는 실시간 전달 대상을 찾기 위한 현재 상태 계층, PostgreSQL은 좌표를 가진 메시지의 영속 계층이다.

데이터 모델 — PostgreSQL + PostGIS

CREATE EXTENSION postgis;

CREATE TABLE message (
  id          BIGSERIAL PRIMARY KEY,
  content     VARCHAR(500)             NOT NULL,
  location    GEOGRAPHY(POINT, 4326)   NOT NULL,
  author_key  CHAR(64)                 NOT NULL,  -- 기기 익명 키 · 절대 미노출
  marker      SMALLINT                 NOT NULL,  -- 0~23 · 구간 내 표식 (D4)
  reply_to_id BIGINT REFERENCES message(id),      -- 인용 답글
  status      TEXT NOT NULL DEFAULT 'visible',    -- visible | hidden | deleted
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_message_loc ON message USING GIST (location);

device       author_key, push_token, updated_at   -- 답글 알림용 (D6)
report       id, message_id, reporter_key, reason, created_at
block        blocker_key, blocked_author_key
banned_area  center GEOGRAPHY(POINT), radius_m, reason  -- 작성 금지 구역
표식은 계산이 아니라 저장이다

marker를 조회할 때마다 계산하면 같은 대화를 다시 봐도 기호가 달라진다. 따라서 작성 시점에 확정해 저장한다. 작성 요청이 오면 같은 구역의 최근 6시간 내 메시지를 조회해 이미 사용 중인 표식을 파악하고, 같은 author_key가 그 구간에 이미 있으면 동일 표식을, 없으면 미사용 표식 중 하나를 배정한다. 6시간 이상 끊기면 새 구간이 시작되어 표식이 초기화된다.

반경 조회 질의

SELECT * FROM message
WHERE ST_DWithin(location, ST_MakePoint(:lon, :lat)::geography, :radius)
  AND status = 'visible'
  AND (:cursor IS NULL OR created_at < :cursor)   -- 위로 스크롤
ORDER BY created_at DESC
LIMIT :limit;
MySQL 대신 PostgreSQL을 쓰는 이유

이 서비스에서 가장 자주 실행되는 연산은 “내 주변 N미터 안의 메시지 찾기”다. MySQL은 ST_Distance_Sphere가 공간 인덱스를 타지 않아, 사각 범위로 1차 필터링한 뒤 거리를 다시 계산하는 우회가 필요하다. PostGIS의 ST_DWithin은 GiST 인덱스를 직접 사용하므로 질의 한 줄로 끝나고 더 빠르다. 또한 GEOGRAPHY 타입이 미터 단위를 직접 다뤄 좌표계 변환이 필요 없다. PostGIS는 공간 데이터 분야의 사실상 표준이며, 이 선택의 타당성은 성능 실험 2에서 수치로 검증한다.

Redis 키 구조

geo:users          GEO    접속자 현재 위치 ← 실시간 전달 대상 선별 (300m)
sess:{userKey}     HASH   세션·연결 정보 (짧은 TTL)

런타임 설정 — 서버가 내려준다

GET /config

{
  "radius_m":           300,   // 조회·전달 반경
  "keep_radius_m":      450,   // 로드된 메시지 유지 범위 (반경 × 1.5)
  "move_threshold_m":    45,   // 화면 갱신을 유발하는 이동 거리 (반경의 1/6~1/8)
  "heartbeat_sec":       45,   // 서버 위치 등록 주기 (화면 갱신과 무관)
  "marker_window_hour":   6
}
값을 앱에 하드코딩하지 않는 이유

반경 값은 실험으로 확정해야 하는데, 앱에 박아 두면 조건을 바꿀 때마다 빌드·배포를 거쳐 테스터 전원이 업데이트해야 한다. 4개 조건을 순차로 테스트하는 것은 현실적으로 불가능하다. 서버가 내려주면 재배포 없이 즉시 바뀌고, 무엇보다 기기 익명 키를 해시해 사용자를 그룹으로 나누는 A/B 실험이 가능해진다. 같은 기간·같은 조건에서 비교하므로 순차 테스트보다 훨씬 깨끗한 데이터를 얻는다. 클라이언트는 시작 시 설정을 받고, 실패하면 내장 기본값으로 폴백한다.

좌표 획득과 지도 렌더링은 별개다. 스밈은 채팅 스크롤이 메인 화면이므로 1단계에서는 지도 SDK를 사용하지 않는다. OS 위치 서비스로 좌표만 받으면 되며, API 키 발급과 결제수단 등록이 모두 불필요하다. 빈 화면 대응은 지도가 아니라 동적 반경 확장과 오래된 메시지 노출로 해결한다. 핫스팟 지도는 출시 이후 확장 기능으로 둔다.

07 — 안전과 익명성

영구 저장의 대가

TTL이 있을 때는 문제 있는 글이 저절로 사라졌다. 영구 저장에서는 특정 좌표에 악의적인 글이 영구히 고정된다. 누군가의 집 앞, 특정 학교, 특정 가게에 비방 글을 남기면 그것이 그 장소의 고정 콘텐츠가 된다. Yik Yak을 무너뜨린 것이 정확히 이 문제다.

따라서 모더레이션은 부가 기능이 아니라 출시 요건이며, 일정상 뒤로 미룰 수 없다.

v1 필수 구현 — 7주차

  • 신고 → 즉시 블라인드 → 검토 파이프라인. 신고 N건 누적 시 자동 숨김
  • 차단 — 이름이 없어도 “이 작성자 글 그만 보기”로 내부 키 기반 필터링
  • 작성자 삭제권 — 기기 익명 키로 본인 글 식별
  • 불쾌 콘텐츠 금지 약관(EULA) 동의 절차
  • 금지 구역 테이블 + 수동 등록 — 데이터는 비어 있어도 되며, 문제 발생 시 즉시 차단할 수단을 확보하는 것이 목적
  • 신고 누적 기반 자동 구역 차단 — 특정 좌표 반경 100m 내 신고 3건 누적 시 자동 등록. 사전 데이터가 필요 없고 운영하며 자라난다
  • 개인 실명·주소 언급 금지 규칙 (Jodel 방식)
  • 개발자 연락처 공개 및 신고 24시간 내 조치

확장 범위 — 출시 이후

  • 전국 학교 좌표 일괄 등록 (공공데이터포털 표준데이터)
  • 용도지역 기반 주거전용지역 제외 — GIS 폴리곤 처리가 필요해 비용이 크다
  • 고밀도 지역의 시간 축 매몰 — 한 장소에 메시지가 수천 개 쌓이면 첫 화면이 당일 것으로만 채워져 오래된 기록에 닿지 못한다. 시간 구간별 배분 또는 과거 대표 글 노출로 대응한다. 사용자 수만 명 규모에서 발생하므로 본 프로젝트 기간에는 나타나지 않는다

위치 프라이버시

  • 정확한 좌표는 서버 내부에서만 사용하고 사용자 간 공유하지 않는다
  • 다른 사용자의 위치를 일절 표시하지 않는다
  • 백그라운드 위치 권한을 요구하지 않는다. 앱이 열려 있을 때만 위치를 사용
  • 실험용 이동 로그는 좌표 원본을 저장하지 않는다. 이동 거리와 화면 전환 횟수만 집계해 전송하며, 수집 항목과 보존 기간을 개인정보처리방침에 명시한다
  • 핫스팟 지도를 확장으로 추가할 경우 k-익명성 임계값을 적용한다 (셀 내 10명 미만 미표시)

테스터 시계가 일정을 지배한다

2023년 11월 13일 이후 생성된 Google Play 개인 개발자 계정은, 프로덕션 출시 전 테스터 12명이 연속 14일간 옵트인을 유지하는 비공개 테스트를 완료해야 한다.

일정 최대 제약

이 14일은 돈으로도 실력으로도 줄일 수 없는 순수 달력 시간이다. 배포 시점(10주차)에 시작하면 12주차 이후에나 출시가 가능하다. 따라서 앱이 완성되기 전인 6주차에, 불완전한 빌드로 비공개 테스트를 먼저 시작한다. 중요한 것은 완성도가 아니라 시계를 미리 돌리는 것이며, 테스트 기간 중에도 앱은 계속 갱신할 수 있다.

대안 — 테스터 12명 확보가 불확실하면 App Store로 전환한다. 연 $99로 비용은 높지만 테스터 요건이 없다. 단 익명 UGC에 대한 심사가 훨씬 엄격해 리젝 시 3~7일씩 왕복하므로, 확실성과 비용을 맞바꾸는 선택이다.

일정 설계의 근거

  • 배포를 10주차 → 5주차로 당겼다. 비공개 테스트를 하려면 테스터가 실제로 앱을 써야 하고, 그러려면 서버가 인터넷에 떠 있어야 한다. 배포는 마무리 작업이 아니라 테스트의 전제조건이다. 10주차에 처음 배포하면 도메인·인증서·방화벽에서 하루씩 날아간다
  • 6주차를 MVP 동결 지점으로 삼았다. 1인 프로젝트의 최대 위험은 기술 난이도가 아니라 기능 욕심이다. 이후 5주는 안정화·실험·출시에만 쓴다
  • 8주차를 통째로 안정화에 배정했다. GPS 오차와 네트워크 전환 문제는 기능 개발 틈틈이 잡히지 않는다
  • 실험 데이터는 6~9주차에 걸쳐 쌓인다. 9주차는 수집이 아니라 분석 주차다. 그래서 /config와 로그 수집이 6주차 이전에 들어가야 한다
  • 실기기 테스트를 6주차 주 작업으로 격상했다. GPS 오차는 시뮬레이터에서 드러나지 않는다
  • FCM 푸시를 확장으로 분리했다. 대신 인앱 답글 표시를 MVP에 남겨 재방문 구조의 최소선을 유지한다 (D6)
  • 플랫폼을 Android 단독으로 축소했다. React Native이므로 iOS 확장 비용은 낮다

10 — 리스크

무엇이 이 프로젝트를 실패시키는가

악용된 영구 콘텐츠

특정 좌표에 비방·괴롭힘 글이 영구 고정된다. Yik Yak의 실제 사인이며, 이 프로젝트 최대 위험.

모더레이션을 7주차로 전진 배치. 신고 시 즉시 블라인드, 신고 누적 시 해당 구역 자동 차단.

테스터 14일 시계 지연

6주차에 비공개 테스트를 시작하지 못하면 11주 내 출시가 불가능해진다. 테스터 12명 모집 실패 위험도 포함.

1주차에 계정 생성 완료. 테스터 명단을 3주차까지 확보하고, 이탈 대비 15명 이상 모집. 확보 실패 시 App Store로 전환.

GPS 오차로 인한 화면 흔들림

도심 GPS 오차는 20~50m, 건물 사이에서는 100m를 넘는다. 반경이 좁으면 사용자가 정지해 있어도 메시지가 나타났다 사라진다. 시뮬레이터에서는 드러나지 않는다.

반경 하한 200m 적용, 좌표 이동 평균, 정확도 낮은 측정 폐기, 일정 거리 이상 이동 시에만 갱신. 6주차 실기기 야외 테스트로 검증.

Oracle Cloud ARM 인스턴스 생성 실패

프리티어 ARM은 리전 용량 부족으로 생성이 거부되는 경우가 잦다. 10주차에 발견하면 일정 전체가 밀린다.

1주차에 인스턴스를 실제로 띄워 확인. 실패 시 대체 리전 또는 저가 VPS를 미리 확정.

밀도 불균형

영구 저장으로 시간이 해결해 주지만, 프로젝트 기간 내에는 여전히 빈 지역이 존재한다.

동적 반경(D2)으로 완화. 시연 범위를 캠퍼스 한 곳으로 좁히고, 사전 시딩으로 초기 콘텐츠 확보.

모바일 WebSocket 불안정

앱이 백그라운드로 가면 소켓이 종료되고, 셀룰러↔Wi-Fi 전환 시 연결이 끊긴다.

5주차에 재연결·Heartbeat·미수신 메시지 복구를 함께 설계. 영구 저장 구조라 복구가 단순하다.

11 — 기대 효과

서비스 측면

장소에 귀속된 기록이라는, 기존 서비스가 담지 못한 그릇을 만든다. 사용자는 채팅방을 고르거나 사람을 찾지 않고, 자신이 서 있는 자리에서 이전에 온 사람들의 이야기를 읽는다. 시간이 지날수록 각 장소의 내용이 두터워지므로 사용자 수가 아니라 경과 시간이 서비스의 자산이 되는 구조다. 재방문은 관계가 아니라 내 흔적에 돌아온 반응이 만든다(D6).

기술 측면

WebSocket 연결 관리와 선택적 브로드캐스트, Redis GEO와 PostGIS의 계층 분리, 동적 반경 산출, 동시 접속 처리, Docker 기반 배포와 CI/CD까지 설계 선택을 측정으로 뒷받침하는 경험을 확보한다. 모더레이션과 스토어 심사 대응 역시 실제 출시에서만 얻을 수 있는 경험이다.

한 줄 소개

스밈은 좌표에 남겨진 익명의 대화를, 그 자리에 갔을 때만 읽을 수 있는 위치 기반 커뮤니케이션 서비스다. 지금 근처에 있는 사람에게는 실시간 대화로, 나중에 오는 사람에게는 기록으로 도착한다.

발표용 — “사람을 찾아 채팅하는 것이 아니라, 그 자리에 남은 이야기를 읽는다.”
