# 01. 위치 기반 검색 — PostGIS를 고른 이유

> 2026-09 · 설계 확정 (질의 구현은 4주차)
> 이 서비스에서 가장 자주 실행되는 연산은 **"내 주변 N미터 안의 메시지 찾기"** 다.
> 앱을 열 때마다, 사용자가 움직일 때마다 돈다. 여기가 느리면 전부 느리다.

---

## 처음엔 MySQL로 잡았다

익숙하다는 이유였다. MySQL 8도 공간 타입과 공간 인덱스를 지원한다.

```sql
SELECT * FROM message
WHERE ST_Distance_Sphere(location, POINT(:lon, :lat)) <= :radius;
```

**그런데 이 쿼리는 공간 인덱스를 타지 않는다.** `ST_Distance_Sphere` 는 두 점 사이의 거리를
계산하는 함수일 뿐이라, 옵티마이저 입장에서는 모든 행에 대해 계산해 봐야 아는 값이다.
메시지가 100만 건이면 100만 번 계산한다.

인덱스를 타게 하려면 우회가 필요하다.

```sql
WHERE MBRContains(:box, location)        -- ① 사각 범위로 1차 필터 (인덱스 사용)
  AND ST_Distance_Sphere(...) <= :radius -- ② 그 결과에만 정밀 거리 계산
```

사각형을 직접 만들어야 하고, 두 단계라는 걸 코드를 읽는 사람이 알아야 한다.
**쿼리 하나에 "왜 이렇게 썼는지"를 주석으로 달아야 하는 구조**가 된다.

## PostGIS는 한 줄로 끝난다

```sql
WHERE ST_DWithin(location, ST_MakePoint(:lon, :lat)::geography, :radius)
```

`ST_DWithin` 은 **GiST 인덱스를 직접 사용**한다. 내부적으로 경계 상자 필터와 정밀 계산을
함께 하지만 그건 PostGIS가 알아서 한다.

```sql
CREATE INDEX idx_message_location ON message USING GIST (location);
```

## geography vs geometry

PostGIS에는 좌표를 담는 타입이 둘이다. 이 선택도 갈렸다.

| | `geometry` | `geography` |
|---|---|---|
| 좌표계 | 평면 | 지구 타원체 |
| 거리 단위 | 좌표계 단위 (도 또는 m) | **항상 미터** |
| 정확도 | 투영법에 따라 다름 | 위도와 무관하게 일정 |
| 속도 | 빠름 | 조금 느림 |

`geometry` 를 SRID 4326(위경도)로 쓰면 거리 단위가 **도(degree)** 가 된다.
"300m"를 도로 환산해야 하는데, **위도에 따라 1도의 실제 거리가 달라진다.**
한국(위도 37°)에서 경도 1도는 약 88km, 적도에서는 약 111km다.

보정하려면 투영 좌표계(예: EPSG:5186)로 변환해야 하고, 그러면 변환 코드와 좌표계 지식이 계속 따라붙는다.

`geography` 는 그냥 미터로 받는다.

```sql
location  GEOGRAPHY(POINT, 4326)
...
ST_DWithin(location, :point::geography, 300)   -- 300 = 300미터
```

속도는 조금 느리지만 **이 프로젝트 규모에서 체감되지 않고, 틀릴 여지가 사라지는 쪽이 중요하다**고
판단했다. 좌표계 변환은 조용히 틀리기 쉬운 종류의 버그다.

## 좌표 순서에서 한 번 헷갈렸다

DB에 직접 넣어보며 확인하다가 겪었다.

```sql
ST_MakePoint(126.9238, 37.5563)   -- (경도, 위도) ← 이 순서
```

**경도가 먼저다.** 위경도를 말할 때는 "위도 37.5, 경도 126.9" 순서로 읽는데
함수는 `(x, y)` = `(lon, lat)` 순서를 받는다. 바꿔 넣으면 서울이 아니라 바다 한가운데에 찍힌다.

에러가 안 나고 **그럴듯한 좌표가 나오기 때문에** 더 위험하다. DBeaver의 Spatial 뷰로
지도에 찍어 확인하는 습관을 들였다.

```sql
SELECT id, content, location::geometry AS geom, created_at FROM message;
```

`geography` 컬럼은 그대로 보면 바이너리라, `::geometry` 로 캐스팅해야 지도 뷰가 뜬다.

## 반경을 밀도에 따라 바꾸려다 폐기했다

초안에서는 **동적 반경**을 설계했다. "주변 메시지가 30개 모일 때까지 반경을 넓힌다."

밀도 편차 때문이었다. 번화가 300m와 시골 300m는 메시지 수가 극단적으로 다르다.
번화가는 쏟아지고 시골은 비어 있으니, 개수를 기준으로 맞추면 어디서든 화면 밀도가 일정해진다.

**그런데 이 설계는 서비스의 전제를 깨뜨린다.**

시골에서 30개를 채우려면 반경이 8km까지 늘어난다. **8km 떨어진 곳을 "그 자리"라고 부를 수 없다.**
"그 자리에 가야만 읽힌다"는 약속이 무너지는 순간이다.

그리고 다시 보니 동적 반경은 **TTL이 있던 시절의 설계**였다. 메시지가 몇 시간 만에 사라지면
주변에 사람이 없을 때 화면이 정말로 빈다. 영구 저장으로 바꾼 뒤에는 같은 자리에 시간이 쌓이므로
화면이 비지 않는다.

→ **공간은 고정하고 시간을 푼다.**

```
번화가 300m    →  첫 화면이 당일 것으로 참
한적한 곳 300m  →  첫 화면이 몇 년치로 채워짐
```

부수적으로 설계가 크게 단순해졌다. 모든 사용자가 같은 반경을 쓰므로
**A가 B를 보면 B도 A를 본다** — 반경이 달라서 생기던 비대칭이 사라지고,
조회와 실시간 전달의 경로를 나눌 필요도 없어졌다.

> 반경 300m는 기본값이고 확정값이 아니다. 100 / 150 / 300 / 500m 를
> 실제 이동 로그로 비교해 정한다. → [`docs/location-policy.md`](../location-policy.md)

## 정리

- `ST_Distance_Sphere` 만으로는 인덱스를 못 탄다. **함수가 인덱스를 쓰는지 따로 확인해야 한다**
- `geography` 는 조금 느린 대신 **틀릴 여지를 없앤다**. 이 규모에서는 후자가 낫다
- `ST_MakePoint` 는 `(경도, 위도)` 순서다. 틀려도 에러가 안 난다
- 동적 반경은 사용성 문제를 풀려다 **서비스의 전제를 깨뜨렸다.** 기술적으로 가능한 것과
  해야 하는 것은 다르다
