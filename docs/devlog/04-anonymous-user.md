# 04. 익명 사용자 처리

> 2026-09 · 기기 키 구현 완료, 표식 배정은 4주차
> 계정이 없는 서비스에서 **"내 글 삭제"와 "이 사람 차단"을 어떻게 하는가.**
> 그리고 이름 없이 대화를 어떻게 읽히게 하는가.

---

## 표시상의 익명과 서버의 무지는 다르다

처음엔 "완전 익명"이라고만 생각했다. 그런데 기능을 나열해 보니 셋 다 식별자를 요구했다.

| 기능 | 필요한 것 |
|---|---|
| 내가 쓴 글 삭제 | 이 글을 누가 썼는지 |
| 이 작성자 차단 | 같은 사람의 글을 묶는 수단 |
| 도배 방지 | 같은 주체의 요청 횟수 |

**차단은 스토어 심사 필수 요건**이라 뺄 수도 없다.

그래서 경계를 다시 그었다.

> **화면에 표시하지 않는다. 서버는 안다.**
> 완전 익명(anonymous)이 아니라 **가명(pseudonymous)** 이다.

이 구분을 개인정보처리방침에도 그대로 쓴다. "익명"이라고 써 놓고 식별자를 보관하면 거짓말이 된다.

---

## 기기 키 — 서버는 원본을 모른다

앱이 최초 실행 시 32바이트 난수를 만들어 보관하고, 모든 요청에 헤더로 보낸다.

```ts
const bytes = await getRandomBytesAsync(32);
const key = btoa(String.fromCharCode(...bytes));
await SecureStore.setItemAsync('smim.deviceKey', key);
```

`expo-secure-store` 는 iOS Keychain / Android Keystore에 저장한다. 앱 데이터를 지우면 키도 사라지고,
**그러면 이전 글의 삭제 권한도 사라진다.** 불편해 보이지만 의도된 동작이다 —
계정이 없으니 복구 수단도 없는 게 일관된다.

서버는 받은 키를 **해시해서만** 쓴다.

```java
public static String toAuthorKey(String header) {
    if (header == null || !isValid(header)) {
        throw new ApiException(ErrorCode.INVALID_DEVICE_KEY);
    }
    byte[] hash = MessageDigest.getInstance("SHA-256")
            .digest(header.getBytes(StandardCharsets.US_ASCII));
    return HexFormat.of().formatHex(hash);
}
```

**원본 키는 어디에도 저장하지 않는다.** DB가 통째로 유출돼도 키 자체는 복원되지 않는다.
길이 검증(base64 디코딩 후 32바이트)도 같이 해서, 아무 문자열이나 보내 `author_key` 를
만들어내는 것을 막았다.

### 실수했던 것 — 실패한 Promise를 캐싱했다

키 조회를 매번 하지 않으려고 Promise를 캐싱했는데, **처음 한 번 실패하면 영원히 실패**했다.

```ts
let cached: Promise<string> | null = null;

export function getDeviceKey(): Promise<string> {
  if (!cached) {
    // 실패한 Promise 를 붙잡고 있으면 다음 호출도 계속 실패하므로 비운다
    cached = loadOrCreate().catch((e) => {
      cached = null;
      throw e;
    });
  }
  return cached;
}
```

SecureStore 접근이 일시적으로 실패할 수 있는데(기기 잠금 상태 등), 그 실패한 Promise가
캐시에 남아 재시도가 불가능해진다. `catch` 에서 캐시를 비워 다음 호출이 다시 시도하게 했다.

## `author_key` 는 어떤 응답에도 넣지 않는다

이게 가장 중요한 규칙이다. 내려주는 순간 **클라이언트가 같은 사람의 글을 묶을 수 있게 되고**,
무기명이 무너진다. 서버가 계산해서 결과만 준다.

| 필요한 것 | 노출 대신 |
|---|---|
| 내 글 구분 | `isMine: boolean` |
| 차단 대상 지목 | 클라이언트가 **메시지 id** 를 보내면 서버가 작성자를 찾아 처리 |

```jsonc
// POST /blocks
{ "messageId": 1287 }
```

차단을 메시지로 지목하는 건 우회처럼 보이지만, `author_key` 를 숨기려면 이 방법뿐이다.

**대가도 있다.** 차단 목록 화면에서 "누구를 차단했는지" 보여줄 게 없다.
차단 시점의 메시지 내용을 함께 보여주는 정도가 최선이다.

로그에도 조심해야 한다. 좌표와 키는 DEBUG로만, 그것도 앞 8자만 남긴다.

```java
log.debug("presence session={} author={}… lat={} lon={}",
        req.sessionId(), authorKey.substring(0, 8), req.lat(), req.lon());
```

## 이름 없이 발화자를 구분하기

여기가 설계에서 가장 오래 걸린 부분이다.

### 닉네임을 넣으면 벗어나려던 구조로 돌아간다

이름은 아무리 무의미해도 정체성을 만들고, 정체성은 관계를 만든다.
그러면 "공간 중심"에서 다시 "사람 중심"으로 돌아간다.

게다가 **위치 기반이라 같은 사람을 다시 만날 확률이 낮다.** 닉네임을 붙여도 관계는 안 생기고
익명의 자유만 잃는다 — 가장 나쁜 절충이다.

### 그렇다고 아무 표시도 없으면 대화가 안 읽힌다

```
  여기 사람 진짜 많네요
  무슨 행사 있나요
  몰루
  버스킹 하는 듯
```

두 명인지 네 명인지 알 수 없다.

### 도형과 색, 그리고 구간

```
도형 6종  ● ▲ ■ ◆ ★ ⬢
색  4종   틸 · 클레이 · 앰버 · 슬레이트
        = 24가지
```

이름이 아니라 **표식**이라는 게 핵심이다. 읽는 사람이 "저 사람"이 아니라 "저 줄"로 인식한다.

**도형을 먼저 다 쓴 뒤 색을 더한다.** 색각 이상이 있어도 도형만으로 구분되어야 하기 때문이다.

```java
도형 = marker % 6
색   = marker / 6
```

순서대로 배정하면 이 규칙이 자동으로 지켜진다. 서버는 `marker` 숫자(0~23)만 내려주고
도형·색 매핑은 앱이 한다.

### 전역 유일성은 필요 없다

표식이 24개뿐이라 사용자가 많으면 부족해 보인다. 그런데 **한 화면 구간에 동시에 등장하는
발화자는 보통 3~6명**이고, 시간 구분선이 이미 대화의 경계를 그리고 있다.

```
──── 2025년 4월 12일 ────
  ● 여기 벚꽃 미쳤다
  ▲ ㄹㅇ 지금이 절정인 듯

──── 2025년 12월 3일 ────
  ● 지금은 눈 옴 ㅋㅋㅋ      ← 위의 ● 와 다른 사람
```

구분선을 사이에 두고 같은 기호가 나와도 동일인으로 오해하지 않는다.
**구간마다 표식을 처음부터 다시 배정**하므로 전체 사용자 수와 무관해진다.

### 표식을 떼지 않는다 — 한 번 뒤집은 결정

처음엔 "시간이 지나면 표식을 떼서, 대화가 기록으로 굳는 과정을 보여주자"고 설계했다.

**논리가 틀렸다.** 지금 읽는 데 표식이 필요했다면 3개월 뒤 읽는 사람에게도 필요하다.
필요해서 붙였다가 나중에 떼는 건 앞뒤가 맞지 않는다.

→ **표식은 메시지에 영구히 저장한다.** 대신 범위를 구간으로 한정해 정체성이 축적되지 않게 한다.

### 계산하지 않고 저장한다

조회할 때마다 계산하면 같은 대화를 다시 봐도 기호가 달라진다. 작성 시점에 확정해 저장한다.

```sql
marker  SMALLINT NOT NULL CHECK (marker BETWEEN 0 AND 23)
```

```
1. 같은 구역 · 최근 6시간 내 메시지 조회
2. 같은 author_key 가 이미 있으면 → 동일 표식
3. 없으면 → 미사용 표식 중 배정 (도형 우선)
4. 6시간 이상 끊기면 새 구간 → 초기화
```

> 이 배정에는 **동시성 문제**가 있다. 두 사람이 같은 순간에 같은 구역에 쓰면
> 같은 표식을 받을 수 있다. → devlog 05에서 다룬다.

## 렌더링 — 문자로 그리면 안 된다

`●▲■◆★⬢` 를 텍스트로 쓰면 기기·OS 폰트에 따라 결과가 달라진다.

- `★` 는 안드로이드에서 **컬러 이모지로 바뀌는** 경우가 있다
- `⬢` (U+2B22) 는 글리프가 없는 폰트가 많다
- 크기와 베이스라인이 기호마다 제각각이다

그래서 `react-native-svg` 로 직접 그렸다. 도형 6개짜리 컴포넌트 하나면 끝나고,
크기·색·정렬이 기기와 무관하게 고정된다.

```tsx
case 'star':
  return <Path d="M8 2 L9.53 5.9 L13.71 6.15 ..." fill={color} />;
```

내 글에는 표식을 붙이지 않고 **오른쪽 정렬로만** 구분한다. 남은 구분되지 않고 나만 구분된다.

## 정리

- "익명"과 "서버가 모른다"는 다르다. **표시하지 않되 보관한다**를 명확히 하고 방침에도 그대로 쓴다
- 원본 키는 저장하지 않는다. 해시만으로 삭제·차단·도배 방지가 전부 된다
- `author_key` 를 응답에 넣지 않으려면 차단을 **메시지로 지목**해야 한다. 불편하지만 대안이 없다
- 이름 대신 표식. **이름은 정체성을 만들고 도형은 만들지 않는다**
- 필요해서 붙인 것은 나중에도 필요하다. 표식을 떼려던 설계는 논리가 맞지 않아 뒤집었다
- 유니코드 도형을 텍스트로 렌더링하지 않는다. 기기마다 다르게 나온다
