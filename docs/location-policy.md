# 위치 정책 및 런타임 설정

스밈의 반경 정책, 위치 갱신 규칙, 서버 설정 스펙, 반경 결정 실험 계획.

- 관련 설계 결정: **D1**(사용자 중심 반경), **D2**(반경 고정), **D3**(영구 저장)
- 최종 수정: 2026-09-16

---

## 1. 반경 정책

### 1-1. 값

| 항목 | 기본값 | 설명 |
|---|---|---|
| `radius_m` | **300** | 조회·실시간 전달 공통 반경 |
| `keep_radius_m` | **450** | 로드된 메시지를 화면에 유지하는 범위 (`radius_m` × 1.5) |
| `move_threshold_m` | **45** | 화면 갱신을 유발하는 이동 거리 (`radius_m`의 1/6 ~ 1/8) |

`radius_m`을 바꾸면 나머지 둘도 비례해서 바꾼다. 실험 조건별 권장값:

| `radius_m` | `keep_radius_m` | `move_threshold_m` |
|---:|---:|---:|
| 100 | 150 | 15 |
| 150 | 225 | 20 |
| 300 | 450 | 45 |
| 500 | 750 | 70 |

> `move_threshold_m`을 반경에 비례시키지 않으면 조건 간 비교가 공정하지 않다.
> 이동 50m 기준으로 화면에서 교체되는 메시지 비율은 반경 300m에서 약 11%,
> 150m에서 21%, 100m에서 31%다. 임계값을 고정하면 작은 반경 조건만
> 유독 산만하다는 결과가 나오고, 그것이 반경 탓인지 임계값 탓인지 구분할 수 없다.

### 1-2. 밀도에 따라 조정하지 않는다

반경은 고정이다. 메시지가 적은 지역에서 **반경을 넓히지 않고, 시간 범위가 넓어지도록** 둔다.

```
번화가 300m    →  첫 화면이 당일 것으로 참
한적한 곳 300m  →  첫 화면이 몇 년치로 채워짐

같은 공간, 다른 시간 폭
```

밀도 기반 동적 반경을 쓰면 한적한 지역에서 반경이 수 km까지 늘어나 "그 자리"라는 전제가
무너진다. 영구 저장(D3)을 택했으므로 같은 자리에 시간이 쌓이며, 화면이 비지 않는다.

### 1-3. 유지 반경 (`keep_radius_m`)

**한 번 화면에 로드된 메시지는 사용자가 `keep_radius_m` 밖으로 나갈 때까지 제거하지 않는다.**

GPS 오차로 경계 근처 메시지가 나타났다 사라지며 화면이 깜빡이는 것을 막는다.
이 장치가 있어야 반경을 작게(100~300m) 잡을 수 있다.

```
신규 추가   거리 <= radius_m
유지        거리 <= keep_radius_m   (이미 로드된 것)
제거        거리 >  keep_radius_m
```

## 2. 위치 갱신 정책

**화면 갱신과 서버 등록은 목적이 다르므로 분리한다.**

| | 목적 | 트리거 |
|---|---|---|
| **화면 재조회** | 보이는 메시지 갱신 | `move_threshold_m` 이상 이동 시 **(거리 기준만)** |
| **서버 위치 등록** | 실시간 전달 대상에 포함 | `heartbeat_sec` 주기 |

### 2-1. 시간 주기로 화면을 재조회하지 않는다

도보 속도(4km/h)로 10초는 약 **11m** 이동이며, 이는 GPS 오차(도심 10~20m)보다 작다.
시간 기준 재조회는 대부분 실제 이동이 아닌 노이즈이며 배터리만 소모한다.

### 2-2. OS 거리 필터에 위임한다

타이머로 GPS를 폴링하지 말고, OS가 지정 거리만큼 움직였을 때 깨우도록 한다.

| 플랫폼 | API |
|---|---|
| Android | `LocationRequest.setMinUpdateDistanceMeters()` |
| iOS | `CLLocationManager.distanceFilter` |
| React Native | `expo-location` → `watchPositionAsync({ distanceInterval })` |

### 2-3. 좌표 스무딩

- 최근 3~5개 좌표의 이동 평균을 사용
- `accuracy` 값이 임계치보다 나쁜 측정은 폐기
- 백그라운드 위치 권한은 요청하지 않는다 (앱이 열려 있을 때만 사용)

## 3. 런타임 설정 엔드포인트

### 3-1. 스펙

```http
GET /config
```

```json
{
  "group": "B",
  "radius_m": 300,
  "keep_radius_m": 450,
  "move_threshold_m": 45,
  "heartbeat_sec": 45,
  "marker_window_hour": 6
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `group` | string | A/B 실험 그룹. 로그에 함께 기록한다 |
| `radius_m` | int | 조회·전달 반경 |
| `keep_radius_m` | int | 로드된 메시지 유지 범위 |
| `move_threshold_m` | int | 화면 갱신 유발 이동 거리 |
| `heartbeat_sec` | int | 서버 위치 등록 주기 |
| `marker_window_hour` | int | 표식 구간 경계 (D4) |

### 3-2. 클라이언트 규칙

1. 앱 시작 시 `/config`를 호출해 설정을 받는다
2. 실패하면 **내장 기본값으로 폴백**한다 (위 표의 기본값)
3. 받은 설정은 세션 동안 캐시하고, 다음 시작 시 갱신한다
4. 설정이 바뀌어도 앱을 재설치할 필요가 없어야 한다

### 3-3. 값을 하드코딩하지 않는 이유

반경은 실험으로 확정해야 하는 값이다. 앱에 박아 두면 조건을 바꿀 때마다
빌드 → 배포 → **테스터 전원 업데이트**가 필요하다. 12명이 모두 업데이트해야 하고
누락되면 데이터가 섞이므로, 4개 조건을 순차 테스트하는 것은 현실적으로 불가능하다.

## 4. A/B 그룹 배정

기기 익명 키(`author_key`)를 해시해 그룹을 결정한다. 동일 기기는 항상 같은 그룹에 속한다.

```
group_index = hash(author_key) % 4

0 → A : radius_m = 100
1 → B : radius_m = 150
2 → C : radius_m = 300
3 → D : radius_m = 500
```

`keep_radius_m`과 `move_threshold_m`은 1-1의 비례 규칙에 따라 함께 결정한다.

> 순차 테스트(1주씩 조건 변경)보다 **동시 병행이 훨씬 깨끗하다.**
> 같은 기간, 같은 날씨, 같은 사용자 활동 패턴에서 비교되기 때문이다.
> 비공개 테스트 기간(6~8주차)에 자연스럽게 데이터가 쌓인다.

## 5. 반경 결정 실험 (성능 실험 3)

### 5-1. 조건

| 그룹 | 반경 | 의도 |
|---|---:|---|
| A | 100m | 장소성 최대. 화면 전환이 과도할 가능성 |
| B | 150m | 골목·출구 단위 |
| C | 300m | 기본값. 작은 상권 단위 |
| D | 500m | 전환 빈도 하한 확인용 |

### 5-2. 측정 지표

| 지표 | 정의 |
|---|---|
| **시간 폭** | 첫 화면에 표시된 메시지가 걸치는 기간 |
| **화면 전환 횟수** | 세션당 `move_threshold_m` 초과 이동으로 재조회된 횟수 |
| **세션 길이** | 앱을 열고 닫기까지의 시간 |
| **작성 전환율** | 열어본 세션 중 메시지를 쓴 비율 |
| **배터리 소모** | 세션 시간당 배터리 감소율 |

### 5-3. 로그 스키마

```jsonc
// POST /logs/session  (세션 종료 시 일괄 전송)
{
  "group": "C",
  "radius_m": 300,
  "session_sec": 214,
  "refresh_count": 3,          // 화면 재조회 횟수
  "distance_moved_m": 180,     // 총 이동 거리 (좌표 아님)
  "span_hours": 51840,         // 화면에 걸친 시간 폭
  "messages_loaded": 48,
  "messages_written": 1,
  "battery_delta_pct": 2
}
```

### 5-4. 개인정보 주의

> **좌표 원본을 절대 저장하지 않는다.** 이동 경로는 민감 정보다.
>
> - 전송 항목은 **이동 거리와 횟수 집계**로 한정한다
> - 어느 지점을 지났는지 복원할 수 있는 데이터를 남기지 않는다
> - 수집 항목·목적·보존 기간을 개인정보처리방침에 명시한다
> - 실험 종료 후 로그를 삭제한다

## 6. 변경 난이도

어떤 값을 나중에 바꿀 수 있고 어떤 것이 못 바꾸는지의 경계.

| 난이도 | 항목 | 방법 |
|---|---|---|
| **쉬움** | 반경, 유지 반경, 이동 임계값, 하트비트, 표식 구간 | 서버 설정 변경 (재배포 없음) |
| **중간** | 신고 임계값, 알림 조건, 정렬 방식 | 서버 배포 |
| **어려움** | 사용자 중심 → 격자 전환(D1), 영구 저장 → TTL(D3), 표식 체계(D4) | 스키마 변경 + 앱 재배포 |

**숫자는 대부분 나중에 바꿀 수 있고, D1~D6 같은 구조 결정은 바꾸기 어렵다.**
따라서 기본값 300m를 지금 완벽하게 고를 필요는 없다. 실험으로 확정한다.

## 7. 미해결 — 고밀도 지역의 시간 축 매몰

한 장소에 메시지가 수천 개 쌓이면 첫 화면이 당일 것으로만 채워지고,
스크롤을 아무리 올려도 오래된 기록에 닿지 못한다.
한적한 지역에서 공간이 무너졌던 것과 대칭으로, 번화가에서는 시간 축이 묻힌다.

**대응 후보**

- 시간 구간별 배분 — 최신 N개 + 과거 구간별 대표 M개
- 과거 대표 글 노출 — 반응이 많았던 오래된 글을 상단 카드로

**우선순위: 낮음.** 사용자 수만 명 규모에서 발생하므로 본 프로젝트 기간에는 나타나지 않는다.
구조만 인지하고 확장 범위로 분리한다.
