# D5. 실시간 전달과 영구 저장을 동시에 수행한다

> 확정 · 2026-09

## 상황

D3에서 메시지를 영구 저장하기로 하자 질문이 생겼다.

> 기록이 남아 있고 나중에 읽는 것이 주된 사용 방식이라면,
> **REST 조회만으로 충분하지 않은가?**

실시간 전달을 넣을 근거가 필요했다.

## 결정

메시지 작성 시 **영구 저장과 실시간 전달을 함께** 수행한다.

```
메시지 작성
  │
  ├──→ PostGIS 영구 저장 ────→ 나중에 오는 사람  = 방명록
  │
  └──→ WebSocket 전달 ───────→ 지금 근처의 사람  = 실시간 대화
       (반경 안 접속자에게만)
```

**같은 메시지가 누가 언제 오느냐에 따라 성격이 달라진다.**

## 대안 — REST 폴링만 (기각)

주기적으로 조회해서 새 메시지를 가져오는 방식. 구현이 단순하고 연결 관리가 필요 없다.

**기각 이유 — 두 가지다.**

**① 지금 근처에 있는 사람들의 대화가 성립하지 않는다.**
폴링 주기만큼 지연되면 주고받는 느낌이 사라진다. 짧게 잡으면 배터리와 서버 부하가 늘어난다.

**② 이 프로젝트의 기술적 중심이 사라진다.**
위치 기반 선택적 브로드캐스트는 성능 실험의 대상이기도 하다. 폴링으로 가면
"위치 기반 실시간 통신"이라는 주제 자체가 없어진다.

## 결과

### 전달 대상을 공간으로 고른다

전체 사용자에게 뿌리지 않고 반경 안의 접속자만 골라 보낸다.

```
접속자 1000명
   ↓  공간 질의
반경 300m 안 30명
   ↓
30명에게만 전달
```

메시지 하나가 만드는 전송량이 접속자 수와 무관하게 유지된다.

### 접속자 위치를 담는 계층이 따로 필요해졌다

"지금 접속해 있는 사람의 위치"는 메시지와 성격이 다르다. 사라져도 되고, 갱신이 잦다.
`PresenceStore` 인터페이스 뒤에 두고 PostgreSQL 구현과 Redis GEO 구현을 교체할 수 있게 했다.

```java
public interface PresenceStore {
    void upsert(String sessionId, String authorKey, Point location);
    void touch(String sessionId);                 // 하트비트
    List<String> findSessionsWithin(Point center, int radiusM);
    void remove(String sessionId);
    int purgeStale(Duration olderThan);
}
```

→ [`docs/tracks.md`](../tracks.md)

### 저장과 전달을 같은 트랜잭션에 묶지 않는다

Redis는 JPA 트랜잭션에 참여하지 않는다. 묶어 두면 구현을 바꿀 때 동작이 달라진다.

```java
// 저장 커밋 후에 조회한다
messageService.save(msg);          // @Transactional
presenceStore.findSessionsWithin(...);  // 트랜잭션 밖
```

### 재연결 복구가 단순해졌다

영구 저장이 있으므로 연결이 끊겼다 돌아오면 **마지막 수신 시각 이후를 조회**하면 된다.
별도의 미수신 큐가 필요 없다. D3가 D5를 쉽게 만든 경우다.

## 번복

**중간.** WebSocket을 걷어내고 조회만 남겨도 서비스는 동작한다.
초기 사용자가 적을 때는 실시간 전달이 거의 발생하지 않으므로 기능적 손실도 작다.

다만 그때는 **프로젝트의 기술적 정체성이 사라진다.** 이 결정은 사용자 가치보다
프로젝트 목적에 더 크게 묶여 있으며, 시간이 부족해 무언가를 포기해야 할 때
이 구분이 판단 기준이 된다.
