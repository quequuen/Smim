# D1. 반경의 중심은 사용자다

> 확정 · 2026-09

## 상황

"공간 단위로 대화를 묶는다"를 구현하려면 **공간의 경계를 무엇으로 정할지** 먼저 정해야 했다.
경계를 어떻게 긋느냐에 따라 데이터 모델과 전달 로직이 통째로 달라진다.

## 결정

지도를 미리 나누지 않는다. 각 사용자는 **자기 위치를 중심으로 한 반경**을 본다.

**"방"이라는 개체가 존재하지 않는다.** 메시지가 좌표를 가지고, 화면은 내 위치를 중심으로 한
공간 질의의 결과다.

```sql
CREATE TABLE message (
    location  GEOGRAPHY(POINT, 4326) NOT NULL,   -- 방 id 가 아니라 좌표
    ...
);
```

## 대안 — 격자(geohash)로 나누기

지도를 미리 잘라 "같은 칸 = 같은 방"으로 묶는 방식. 구현이 단순하다.

- 방이 실체로 존재해 라우팅이 쉽다
- 참여자 목록이 일관된다
- 같은 칸 구독자에게 뿌리면 끝이라 전달 로직이 간단하다

**기각 이유 — 경계선 문제.**

```
        │ 칸 A        │ 칸 B
        │        ●    │  ●
        │       나    │  상대
        └─────────────┴──────
             50m 떨어져 있는데 서로 안 보임
```

번화가 한복판에 인위적인 선이 그어지고, 바로 옆 사람과 대화가 안 된다.
사용자가 그 선의 존재를 알 방법도 없다. "그 자리"라는 감각이 격자 모양에 지배당한다.

## 결과

- 데이터 모델이 **메시지 = 좌표를 가진 점**으로 단순해졌다. 방 테이블도 참여자 테이블도 없다
- 전달 대상 선별이 공간 질의가 된다 — 구독 목록이 아니라 `ST_DWithin`
- 입장·퇴장 개념이 사라진다. 사용자에게 보여줄 것도, 서버가 관리할 상태도 없다
- **비대칭 문제가 생길 수 있었다.** 사용자마다 반경이 다르면 A는 B를 보는데 B는 A를 못 본다.
  D2에서 반경을 고정하면서 이 문제가 함께 사라졌다

## 번복

**어렵다.** 격자로 바꾸려면 스키마(방 id 컬럼), 전달 로직(구독 기반), 앱 화면이 모두 바뀐다.

다만 이 결정을 되돌릴 이유는 규모가 아주 커졌을 때의 성능 정도인데,
그때는 격자를 **내부 최적화**(공간 인덱스 보조)로 쓰면 되고 사용자에게 노출할 필요는 없다.
